# `cases/` — the preserved-instance corpus

A tool that has never fired on a known-positive input reports a null that means
nothing. 29 of Echo's tools were in that state. This directory holds, for each
tool, the **frozen bytes of an input that actually exhibited the phenomenon the
tool was built to detect**, together with the verdict the tool returned on those
bytes at freeze time.

These are not unit tests. A unit test is an input constructed to make a point. A
case is an input that *made* the point and was kept.

## Why it lives in this repo and not in `~/entity`

`~/entity` has no version control. A case deleted there leaves no trace. Here,
deleting a case requires a branch and a pull request that D merges, and the merge
commit is a dated artefact signed by someone other than the party being audited.

That shape is copied from **42 CFR 493.1274(f)(2)**: a laboratory may discharge
its slide-retention duty by *loaning* the slides to the proficiency-testing
programme that does the challenging, provided it keeps written acknowledgment of
receipt. The repo is the outside custodian; the merge commit is the
acknowledgment (**49 CFR 831.12(b)**, the same artefact in the other direction).

Both registers generate their artefact at the moment custody crosses between two
parties, and neither generates one for the period of *keeping*. A transfer has
two parties; keeping has one. A single principal keeping its own evidence
produces no record at all — which is the whole reason this is a PR and not a
file in the journal.

## The one number

`WINDOW_DAYS` holds a single integer. `runner.py` reads it once, at import, and
uses the same value for two different duties:

| duty | source shape | here |
|---|---|---|
| retention — a case may not go missing inside the window | 42 CFR 493.1105(a)(7)(i)(A), *retain at least five years* | `--check` fails if an in-window case has an empty `input/` |
| re-run — every case inside the window must be executed | 42 CFR 493.1274(c)(3), *review all specimens received within the previous five years* | the runner executes every in-window case; older ones report `STALE` |

Neither CLIA section mentions the other. **The equality of the two five-year
figures is the entire mechanism**, and if they drifted apart the arrangement
would quietly stop working with both clauses still satisfied. So there is
deliberately no second constant here to drift against: change the number in
`WINDOW_DAYS` and both duties move together, or not at all.

## Status: `FROZEN` or `LOST`, and nothing else

- **`FROZEN`** — the bytes in `input/` are the bytes that exhibited the
  phenomenon, recovered from an immutable or versioned store.
- **`LOST`** — the motivating instance was a state of a mutable, unversioned
  file and has already been overwritten. Freezing that file *now* would preserve
  a post-repair state, which is worth nothing as a positive control. The row is
  kept, with no input, so the gap is counted rather than forgotten.

There is no `PENDING`. A to-do list kept inside a corpus reads as coverage.

`LOST` exists because of the case that started this: `tools/rediscover.py`'s
routing-loss detector had exactly one known instance, and that instance had been
*repaired* before anyone thought to keep it. Repairing an accidental finding
destroys the only calibration case it ever provided.

## Layout

```
cases/
  WINDOW_DAYS            the one number
  runner.py              executor, manifest generator, mutation harness
  classify.py            recomputes the corpus denominator from tools/
  MANIFEST.tsv           generated; a mismatch against the tree is a FAIL
  TOOL_INVENTORY.tsv     generated by classify.py
  <tool>/<cNNN>/
      case.json          tool, cycle, status, kind, date_frozen, argv,
                         expected verdict, tool sha256 at freeze, note
      input/             the frozen bytes, laid out relative to a fake root
```

## How a case is executed

Most of Echo's tools compute their root as
`dirname(dirname(abspath(__file__)))`. `abspath` does **not** resolve symlinks.
So the runner creates a temporary directory, symlinks `tools/` into it, copies
the case's frozen `input/` tree alongside, and runs the tool from there — every
root-relative read lands on the frozen copy instead of the live journal. Tools
that take explicit path arguments are simply given them.

Tools that use `Path(...).resolve()` defeat this, and tools that hardcode
`ROOT = "/home/pulse/entity"` defeat it absolutely: they read live state no
matter what is preserved. `classify.py` counts all three classes. That axis is
the one the design note missed — whether an instance can be *recovered* and
whether it can be *delivered* are different questions, and a single word in a
path expression decides the second one.

## Usage

```
python3 cases/runner.py                  # run everything, print coverage
python3 cases/runner.py --tool citeline  # every case for one tool
python3 cases/runner.py --check          # manifest + retention, no execution
python3 cases/runner.py --mutate         # corrupt every input; all cases must FAIL
python3 cases/runner.py --manifest       # regenerate MANIFEST.tsv
python3 cases/runner.py --selftest       # test the runner itself
python3 cases/classify.py                # recompute the denominator
```

`--mutate` is the part that keeps the corpus honest. A case that still passes on
a corrupted input is not measuring its input, and is worthless however green it
looks. For a **negative** control, deletion cannot break a claim of absence, so
the mutation is instead to feed it the sibling *positive* instance for the same
tool: if it still reports clean, it is reporting its own expectation.

## Reading a failure

A case that stops passing is a report that **something moved**. Which of the
tool, the frozen input, or the world moved is then a question, not an answer.
`tool_sha256_at_freeze` in each `case.json` is there to answer the first part of
it: if the hash still matches, the tool is not what changed.
